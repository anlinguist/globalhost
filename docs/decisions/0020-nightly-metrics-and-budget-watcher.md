# ADR-0020: Nightly metrics go to an issue and a bucket, and the budget watcher fails the job

- Status: accepted
- Date: 2026-11-04 (amended the same day for slice 2: cleanup, holds, the projection's pace)
- Relates to: ADR-0004 (budget), ADR-0014 (no API keys), ADR-0016 (identities pinned to the default branch's workflow)

## Context

P1-13 planned a nightly job that commits `docs/metrics.md` and checks the daily spend against the Anthropic Console. A nightly commit to `main` would need a write path around the main ruleset, for a file nobody edits. The Console check as written needs Anthropic's Admin cost API, and that needs an API key, which ADR-0014 rules out. This repo is public, so its issues, Actions logs and anything committed are public too, while the data comes from `run.json` files that hold agent-written text and can name private product repos.

## Decision

- **Output.** `.github/workflows/nightly.yml` (schedule and `workflow_dispatch`, main only) runs `globalhost metrics`. It writes `gs://globalhost-control/metrics/<day>.json` and edits one rolling issue in this repo, title "Factory metrics", label `factory:metrics`, through `GITHUB_TOKEN`. This replaces `docs/metrics.md`. `<day>` is the last complete UTC day, and every total runs through it, so the numbers are final and a re-run gives the same ones.
- **Everything published is aggregate, because it's public.** Nothing agent-written leaves. The job reads only numeric and enum fields from `run.json`, plus repo names that pass the slug regex. It never uses `report`, `problems`, `stopReason`, `model` or any other free-text field. A repo that isn't confirmed public (private, unreadable by the token, or any error asking) is rolled up as `other`, in every table and finding, and doesn't fail the job. Errors logged by the job carry fixed text and an HTTP status, never an object name or API path, because those can name a private repo. Object names of records it couldn't use go only to `metrics/<day>.problems.json` in the private bucket.
- **Its own identity, `sa:globalhost-gh-nightly`.** WIF provider `github/globalhost-nightly` accepts only `nightly.yml` on main in this repo (`job_workflow_ref` and `workflow_ref`), for its two triggers, on a GitHub-hosted runner. It has `objectViewer` on `globalhost-runs` and `globalhost-control`, and `objectUser` conditioned on the `metrics/` prefix of the control bucket. It has no other write and no project-level role. Install and build run before its GCP login.
- **Budget cycle:** the 10th to the 9th, UTC, cap $150 (ADR-0004), committed as constants in `packages/dispatch/src/metrics.ts`. Days 1-9 belong to the cycle that began on the previous 10th.
- **Budget watcher.** After publishing, the job fails, so GitHub emails the owner, and the issue lists why, when any of these holds:
  1. cycle-to-date ledger spend is at least 80% of the cap;
  2. the projection to cycle end exceeds the cap, from day 5 of the cycle. The projection is cycle spend so far plus the average daily spend over the trailing 7 complete UTC days times the days left, so a burst counts in full however quiet the cycle's start was. The window stays inside the cycle: on days 5 and 6 it's that many days, because last cycle's spend isn't this cycle's pace, and it's never empty. The issue names the basis ("Projected $X at the last 7 days' pace");
  3. the last complete day, all repos together, is at least 80% of the default `limits.dailyUsd` ($20 in the schema; ADR-0004's $15 was never what shipped);
  4. over the trailing 7 complete days, the per-turn deltas from `run.json` differ from the ledger by more than max($1, 10% of the ledger). The difference is taken per repo and added up as absolute values, so one repo's excess can't cancel another's shortfall. It compares over a window, not per day, because a run can cross midnight. This compares two records of the same run, so it only sees a gap between them: see the limits below;
  5. a corrupt record in `spend/`, a corrupt PR ledger in `reviews/`, or a `run.json` that fails its schema or disagrees with its object name. These are reported, never skipped;
  6. an open reservation older than 24 hours, on a spend record in the window or in any PR ledger.

  If the job can't read a bucket, it fails without publishing.
- **Console reconciliation is a manual owner check.** No Admin API (ADR-0014). The issue prints cycle-to-date; the owner compares it with the `globalhost-runners` workspace and records the result in PLAN P1-13. Known unledgered spend (`security-audit.yml`, local `globalhost run` and `assess`, and sessions that died mid-run) makes the Console read higher. The issue lists the holds released this cycle, the upper bound on what those sessions spent.
- **`metrics/` and `spend/` objects are deleted after 400 days**, by lifecycle rules limited to those prefixes (`withState: LIVE`). The control bucket is versioned, so such a delete leaves a noncurrent version, which the existing rule removes 30 days later. `spend/` retention is far past anything read: a report needs a cycle plus the drift window. Rewriting a record starts its age again, which only keeps it longer.
- **Cleanup is its own workflow, `.github/workflows/cleanup.yml` (slice 2), with its own identity, `sa:globalhost-gh-cleanup`.** GitHub's `job_workflow_ref` names the file, not the job, so a second job in `nightly.yml` could mint the same tokens as `metrics`, and the read-only identity wouldn't stay read-only. It runs half an hour before `nightly.yml`, so the issue reads what's left. Its grants: `objectViewer` on `globalhost-control` (listing can't take an object-name condition); `objectUser` conditioned on `reviews/`, and on `spend/` (overwriting a record needs delete as well as create, and IAM can't separate them); on each product's dev project, a custom role with `run.services.get` and `run.services.update` on the preview service only, and one with `firebaseauth.configs.get`, `firebaseauth.configs.update` and `serviceusage.services.use` at project level, which is as low as that config goes. Nothing on a prod project or `globalhost-runs`, and no image delete: images (`previews`: untagged 1 day, anything 30 days) and screenshots (30-day lifecycle) age out on their own.
- **Cleanup keys on GitHub's answer.** The product list comes from `infra/factory/Pulumi.prod.yaml`, the same list Pulumi grants on. A `pr-<n>` tag or `<product>-<part>-pr-<n>.globalhost.ai` domain is an orphan only if `GET /repos/<repo>/pulls/<n>` answers cleanly that it closed more than an hour ago, so the workflow's own teardown isn't raced. Anything else (open, 404, a 5xx, a rate limit, an issue's number, a different repo or number in the body, a closed PR with no time) keeps it and reports it. Only exact names match. A tag on a target carrying traffic, or not pinned to a revision, is kept whatever its PR says.
- **Cleanup's writes are conditional where the APIs allow.** Traffic updates send the service as read, with its `etag`, under `updateMask=traffic`, and a conflict re-reads, up to 3 times. Identity Platform's config has no etag or precondition, so domains are re-read immediately before the PATCH, which takes out only the domains judged orphans. A concurrent writer can still interleave in the moment between that read and the write, in which case the last writer wins: the preview workflow's own GET-then-PATCH has the same gap. Object deletes and rewrites match on generation.
- **A closed PR's claims go after 7 days; its ledger stays if it records a review.** A ledger with any `runs` or spend is that PR's shadow index, and its budget if the PR reopens, so it's kept until P2-01c sets its retention. It's small. Only an empty ledger is deleted, with the claims. An open reservation keeps both and is reported. The metrics never read a ledger's spend (cycle spend and drift come from `spend/` and `run.json`), so none of this can change a reported number. Deletes leave noncurrent versions for 30 days.
- **A stale review reservation is released only once its PR is closed and it's over 24 hours old,** through `releaseStaleReservation`, which adds no cost: the run may have spent up to the hold, but nothing knows how much, and its reservation was never in the ledger's `usd`. It's listed under `released` on its day's spend record, in the same write, and the issue reports the count and amount. Open PRs' holds stay, and the watcher reports them.
- **A session holds its cap before it starts.** `dispatch.ts` adds a `kind: "dispatch"` reservation of `limits.perRunUsd` to today's spend record before the Managed Agents session, and `recordSpend` settles it when the run returns. If the runner says no session could exist (`RunNotStartedError`: a clone or upload failure, anything before `createSession`), the hold is given back. If the job is killed, or the run throws once a session may exist, the hold stays, counted against that day's budget, and the watcher reports it after 24 hours. Cleanup releases it after 48, so the owner gets a red night first, and then it's on the issue's released line. A hold on a corrupt record refuses the run.
- **A failed review archives a `run.json`,** when its session may have spent and the normal archive didn't finish: the harness's own record if there is one, or else a minimal one at the cost being settled. So it no longer trips drift, and review $/PR counts it.
- **A hard cap: 20 changes a run,** counting tags, domains, closed PRs' claims and empty ledgers (one per PR), and releases together. Above it the job changes nothing and fails. It's judged on a whole plan: a read that fails is one failure, the other reads still finish and count, and only what was counted is applied. Changing it takes a commit, on purpose.
- **The kill switch stops cleanup's writes too.** When `state.json` says paused, or is corrupt, the job dry-runs whatever `CLEANUP_APPLY` says, and the job summary says why. If the state can't be read, it dry-runs and fails the job.
- **Rollout is the owner's.** `cleanup.yml` writes only when the repo variable `CLEANUP_APPLY` is exactly `true`, and otherwise dry-runs and prints the plan. `CLEANUP_DRY_RUN=1` forces a dry run, for a local run with `gcloud` signed in. Output goes to the job summary and the log, as PR numbers, amounts and fixed text. Counts don't go in the metrics issue, because that would take another write grant for a number the summary already shows; a failure emails the owner, and releases do reach the issue.

## Consequences

- **A session that dies is seen, but its cost isn't known.** Drift still stays at $0 for one, since `recordSpend` and `archive` run only after the session returns. Its hold is what shows: a watcher finding, then a line in the issue. **What it actually spent is visible only in the Console, and the Console workspace limit remains the hard cap.** What remains after giving back a run that never started:
  - A `createSession` that fails may have made a session, so its hold stays, and so does a job killed at any point, even one killed before its session opened. Each takes `perRunUsd` of that day's budget until midnight, and can raise a false finding for a night. At the defaults ($4 of $20), five such failures in a day stop that repo's builders and reviews until midnight.
  - An in-flight builder's hold counts against reviews and other builders in the same repo while it runs, because they share `dailyUsd`. That's stricter than before, and it's the same way a review's hold counts against builders.
  - A resumed run never gives its hold back, since its session already exists.
- **A failed review can still trip drift if its record can't be archived either,** for example when the runs bucket is down. Settling goes ahead regardless, because the ledger must not undercount. The finding names this as a possible cause.
- **Ledgers with reviews accumulate until P2-01c sets their retention.** P2-01c's merge policy and the L3 promotion count (ADR-0015 §12: 20 PRs) read those entries, and it must choose how long they last. Each is small, and each costs one GitHub read a night, to see whether its PR reopened. A PR reopened after a week keeps its per-PR budget, but its claims are gone, so it may re-review a SHA, within that budget.
- **`firebaseauth.configs.update` covers the whole Identity Platform config,** not just the domain list, the same as `preview-deployer`. The code only ever sends `updateMask=authorizedDomains`, so that scoping is self-restraint in trusted code. **`objectUser` on `spend/` includes delete:** a subverted job could remove spend records, though noncurrent versions keep them for 30 days and it can't reach `state.json`.
- **The cleanup identity holds `roles/iam.serviceAccountUser` on `sa:preview-runtime`,** that one service account in the dev project. Cloud Run checks `actAs` on any service update, even a traffic-only one: the first applied run was denied `iam.serviceaccounts.actAs` (2026-11-04, audit log). With `run.services.update`, IAM therefore lets this identity deploy a revision of the preview service running as `preview-runtime`, which has dev data access only. The code only sends `updateMask=traffic`, so that limit is self-restraint in trusted code, as it is for the Identity Platform config.
- **A backlog over the cap stops all cleanup until a commit raises it.** A PR's review state counts once however many claims it has, so one run can delete more objects than the cap, since a long PR's claims alone could otherwise stop cleanup for good. That's the point of a cap, and on this factory's PR volume it shouldn't trip by itself.
- **A midnight crossing at the window's edge can trip drift for a day.** A run that finishes just before the window opens while its spend lands just inside it (or the reverse at the other edge) counts on one side only. It's within the $1 floor unless the run was costly, and it clears on the next night's window.
- **A resumed turn with no baseline turns the drift finding off.** When turn 1 has aged out, the run-record side is known to be short, so the finding is suppressed while that turn is in the window, and the issue says the check didn't run. Real drift in those 7 days goes unreported until the turn leaves the window.
- **A release is seen on the issue only if its day's record is in the spend window.** A hold older than that, on a PR open for weeks, was red every night until then, and its release is in the job summary, not the issue.
- **The owner's main-branch ruleset stays as it is.** Nothing commits nightly, and `GITHUB_TOKEN` can't push from this job (`contents: read`).
- **The job's `GITHUB_TOKEN` can write any issue in this repo.** Its code is pinned to main and takes no untrusted input as instructions, so that scoping is self-restraint in trusted code, as with `REVIEW_PERMISSIONS` (ADR-0018).
- **`objectUser` includes delete under `metrics/`,** because overwriting a day's report needs it. A subverted job could remove old reports; the bucket's versioning keeps them for 30 days. The ledger and kill switch are out of its reach.
- **Run records last 30 days (lifecycle), and a cycle can be 31.** Late in a long cycle, its run-derived numbers (run counts, redirects, review cost) can miss the first days, and the issue says so. Ledger spend, drift and every watcher condition on spend aren't affected. A resumed run whose first turn has aged out has no known baseline: it's counted as a redirect but adds no cost to the run-record figures, and the issue notes it.
- **A corrupt record stays red until the owner fixes or deletes it.** Corrupt spend records are only looked at within the current cycle and drift window.
- **GitHub disables scheduled workflows after 60 days without repo activity.** If the factory repo goes quiet the watcher stops silently, until someone re-enables it.
- **Cost.** Two WIF providers and two service accounts are free, and these are small objects in an existing bucket. Actions minutes are free on a public repo. No new paid resource.
- **Owner setup:** `pulumi up`, then repo variables `GCP_NIGHTLY_WIF_PROVIDER` and `GCP_NIGHTLY_SA`, from `pulumi stack output nightlyWorkloadIdentityProvider` and `nightlyServiceAccount`. The job fails until both are in place. For cleanup, `GCP_CLEANUP_WIF_PROVIDER` and `GCP_CLEANUP_SA` from `cleanupWorkloadIdentityProvider` and `cleanupServiceAccount`, and `CLEANUP_APPLY=true` once a dry run has looked right.
